## Critical

**FD-1 — Folding the mobile bottom sheet hides the legend, violating the standing "always visible" rule (continues C13)**
- Severity: High | Confidence: High | Status: Confirmed
- `web/index.html:339` (`.rail.folded > :not(.sheet-toggle){display:none}`) combined with `web/app.js:1067` (`layoutForSize()` moves `.reading`, which contains `.legend`, to become a direct child of `.rail`)
- CLAUDE.md's design policy says explicitly: "The legend is always visible, never folded into a panel," and lists this as a rule not to revisit without being asked. On screens ≤860px, `layoutForSize()` reparents the entire `.reading` block (readout + legend) inside `.rail`. The fold CSS then hides every direct child of `.rail` except the grab handle, so tapping the handle to fold the sheet — the exact interaction the handle exists for — removes the legend from the screen entirely, on every phone-sized viewport (390×844, 844×390 are two of the four required check sizes in the deploy rule).
- Failure scenario: on a phone, tap the "Departure" panel's grab handle to get the globe full-screen (as the UI invites you to); the legend, and the whole readout, disappears with no way to see it while folded — a direct, reproducible violation of CLAUDE.md, and it would pass `browser_verify.sh`'s viewport checks because that script never folds the sheet.
- Secondary consequence of the same code: `map.on("click", …)` at `web/app.js:791` sets `$("route").open = true` to reveal the route panel, but `<details id="route">` is also a folded-hidden direct child of `.rail`, so tapping a destination while the sheet is folded silently does nothing visible (the other half of the original C13).
- Fix: keep `.legend` (or the whole `.reading` block) as a sibling of `.rail`, not a child, on small screens — e.g. leave `.reading` where it is and only move a compact readout line into the sheet, or add an explicit CSS exception so `.rail.folded > .reading{display:block}`. Also un-fold the sheet (`rail.classList.remove("folded")`) when a destination is set via map click.

## High

**FD-2 — Origin-switch race is still live for 4 of 5 per-origin fetches (C5 not actually fixed)**
- Severity: Medium | Confidence: High | Status: Confirmed
- `web/app.js:483-519`
- Only the newly-added rail fetch checks the generation guard: `if (b && j && active === o) { railDetail = …; }` (lines 483-488). The other four per-origin fetches that assign into the same shared, module-level state — `.bin` → `hoverTimes` (489-499), `.modes.bin` → `hoverModes` (504-507), `.air.bin` → `hoverAir` (508-511), `.json` → `routes` (512-519) — assign unconditionally in their `.then()` with no `active === o` check at all. This is the exact defect cycle-1 flagged (C5), just with the guard added to the one call site that didn't previously exist, while the other four remain exactly as broken.
- Failure scenario: click Seoul, then quickly click Tokyo. If Seoul's `.modes.bin`/`.air.bin`/`.json`/`.bin` responses land after Tokyo's (plausible on any real network — file sizes and cache states differ per origin), Tokyo's freshly-set `hoverModes`/`hoverAir`/`routes`/`hoverTimes` get silently overwritten with Seoul's data while `active`, the city list, and the map tiles all correctly show Tokyo. The reading, route panel and mode breakdown now describe the wrong city with no visible error.
- Fix: capture `o` in each `.then` and guard every assignment the way the rail fetch already does (`if (active === o) { … }`), or introduce a single monotonically-increasing generation counter checked once per callback.

**FD-4 — Preallocated edge-array capacity in `hex_edges`/`native_edges` is sized from a single historical measurement with no bounds check**
- Severity: High (an overflow crashes a multi-hour build with a bare `IndexError`) | Confidence: Medium | Status: Needs manual validation
- `src/transport_maps/graph/ground.py:91-131` (`cap = 8 * len(idx.cells)`), duplicated at `src/transport_maps/contour/grid.py:104-124` (`cap = 8 * len(cells)`)
- Both functions build up to two directed edges per cross-resolution ring neighbour (the fine↔unsplit-base pair, lines 126-130 in `ground.py` / 116-123 in `grid.py`) into fixed-size `np.empty(cap, dtype=…)` arrays with no assertion that `m` stays `<= cap`; `rows[m] = u` will raise `IndexError` if it doesn't. The sizing comment at `ground.py:91-92` cites "82 million edges" as the measurement that motivated preallocation, while `cli.py:81` and `ground.py:41` both describe the current graph as "ten million cells" — 82M/10M ≈ 8.2 edges/cell, i.e. already above the chosen 8×N budget on the numbers quoted in the code's own comments. I could not run the actual build to confirm the true edge count (read-only constraint), so I can't confirm this fires today, but the code pattern itself — an unguarded, hand-picked multiplier standing in for a real worst-case bound — is inconsistent with this codebase's otherwise-consistent practice of bounding and asserting every other silently-growing quantity (`MAX_DROPPED_AIRPORT_FRACTION`, `MAX_UNKNOWN_PAIR_FRACTION`, `MAX_ISOLATED_AIRPORT_FRACTION`, `GateFailure`).
- Failure scenario: a future landmask/refine change increases the split fraction (more urban/road cells) enough to push edges/cell past 8, and a `build-all` that has been running for hours dies with a bare `IndexError: index 80000000 is out of bounds for axis 0 with size 80000000` and no diagnostic — the "no resume, wastes hours" failure class CLAUDE.md's deploy rules are written to avoid.
- Fix: either compute the true worst case (6 same-resolution + a derivable bound on cross-resolution boundary length) or raise a clear `RuntimeError` (`if m > cap: raise …`) before ever writing past capacity, so a future regression aborts with a message instead of a raw index fault.

**FD-5 — Airport-to-land snapping (`_nearest_land`) doesn't search across the fine/base resolution boundary, unlike the codebase's own adjacency rule**
- Severity: Medium | Confidence: Medium | Status: Needs manual validation
- `src/transport_maps/graph/nodes.py:114-128`
- `_nearest_land(cell, cell_pos, lat, lon)` walks `h3.grid_ring(cell, ring)` for `ring in (1, 2)` at `cell`'s own resolution and looks up each candidate directly in `cell_pos`. If the airport's cell is a `FINE_RES` (res-7) cell inside a split base cell, this only ever proposes other res-7 candidates; it never considers the neighbouring unsplit `SOLVE_RES` (res-6) cell the way `refine.ground_adjacent()` (`refine.py:66-83`) and `ground.hex_edges()` (`ground.py:115-130`) explicitly do for the graph's own adjacency. Coastal cities — precisely where airports and the density-driven split boundary both concentrate — are the likely place for an off-mask airport's true nearest land to sit in an adjacent *unsplit* cell rather than another fine cell.
- Failure scenario: an airport whose cell was excluded by the 1:10m coastline cut, sitting in a split (fine-grid) region near the edge of the split zone, has real land two rings away in the unsplit neighbour — `_nearest_land` reports `None`, and the airport is counted as dropped rather than snapped, understating the achievable snap rate and, in aggregate, nudging the graph closer to `MAX_DROPPED_AIRPORT_FRACTION`. There is also no dedicated unit test for `_nearest_land` itself (`tests/graph/test_nodes.py` only asserts an aggregate dropped/total ratio), so a regression here would not be caught surgically, only if it happened to push the total past the 2% abort bound (CLAUDE.md's testing rule: "assume a new test is vacuous until shown otherwise").
- Fix: have `_nearest_land` fall back to `refine.ground_adjacent`-style cross-resolution candidates (the base parent of each fine ring cell, and vice versa) the same way `hex_edges` does, and add a focused test that places a synthetic off-mask airport exactly on a fine/base boundary and asserts it snaps.
