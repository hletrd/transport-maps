## Findings

### PR-1 — `SystemExit` inside a forked pool worker deadlocks `build-all` instead of aborting it
- **Severity:** Critical · **Confidence:** High · **Status:** Confirmed (reproduced)
- **Where:** `/Users/hletrd/flash-shared/transport-maps/src/transport_maps/cli.py:84-87` (`raise SystemExit(f"{slug}: coverage ...")` inside `_solve_one`), `:109-112` (`_solve_one_forked` re-raises it in the child), `:187-191` (`ctx.Pool(workers)` + `pool.imap(_solve_one_forked, origins)`).
- **Why it is a problem:** `multiprocessing.pool.worker` only catches `Exception`. `SystemExit` is a `BaseException`, so it escapes, the worker process exits, the pool's maintenance thread spawns a replacement, and the task's result never arrives. `pool.imap` then blocks forever. Reproduced with a 2-worker fork pool and an 8 s alarm in the scratchpad: the parent printed `got 0` and then hung until the alarm fired (`HUNG: pool.imap never returned after worker raised SystemExit`). The gate that is meant to abort the build ("a partially written dist/ is worse than none") instead leaves it silent at 0 % CPU. The docstring at `cli.py:131-136` promises an abort that the forked path cannot deliver; the tests in `tests/test_cli.py:107-125` pass only because `_worker_count` (`cli.py:64-65`) forces the serial path for fewer than four origins.
- **Observed on this machine (needs manual validation for cause):** eight `.venv/bin/python -u -m transport_maps.cli build-all` processes with PPID 1, state `SN`, 0.37 s of CPU each after 5 h 30 min, ~10 MB RSS. That is the signature of a pool whose parent is gone or blocked, not of a running build. They were not touched.
- **Failure scenario:** one origin out of 553 (say a new GeoNames capital on an islet the land mask lost) comes out below 90 % coverage on hour 6 of a 10-hour build. Nothing is printed, the process never exits, and the operator discovers it the next morning.
- **Fix:** raise `RuntimeError` (or a dedicated `BuildAborted(Exception)`) from `_solve_one`; in `_solve_one_forked` wrap the call in `try/except BaseException` and return a tagged failure that the parent turns into an abort (`pool.terminate()` then `raise`). Use `imap_unordered` (see PR-18) so the failure surfaces as soon as it happens. Add a test that runs `_build_all` with four stubbed origins so the forked path is exercised, and mutate the coverage stub to prove it goes red.

### PR-3 — Every origin's bands make a full GeoJSON round trip through Python tuples: `mapping()` → `json.dump` → tippecanoe → `shape()` again
- **Severity:** High · **Confidence:** High · **Status:** Confirmed (sizes measured on disk; cost measured at small scale)
- **Where:** `/Users/hletrd/flash-shared/transport-maps/src/transport_maps/contour/bands.py:187` (`"geometry": mapping(geometry)` for every feature of every LOD); `/Users/hletrd/flash-shared/transport-maps/src/transport_maps/emit/tiles.py:28-30` (`json.dump(feature_collection, fh)` to `$TMPDIR`); `/Users/hletrd/flash-shared/transport-maps/src/transport_maps/validate.py:87-90` (`shape(f["geometry"])` re-parses the same nested tuples for the cover gate).
- **Why it is a problem:** the GeoJSON text a resolution-5 origin produced was 91–107 MB (five `tmp*.geojson` files left in `$TMPDIR` on 9 Sep 21:06 — see PR-15). Measured on an 11 k-hex dissolved band: `mapping()+json.dumps` costs ~10 s per 100 MB and holds ~159 B per coordinate of transient Python objects, i.e. ~0.4 GB peak per 100 MB of GeoJSON; `shape()` costs another ~1 s per 100 MB. The resolution-6/7 grid has 2.5× the base cells and up to 7× in dense areas, so expect several hundred MB per origin and 1–3 GB of transient tuples per worker, five workers at once. `shapely.to_geojson` produced the same text ~8× faster with no Python object tree.
- **Failure scenario:** five workers hit `_feature` for their densest LOD simultaneously; each spikes 2–3 GB on top of the ~1 GB of un-shared index pages (PR-7). On the 32 GB machine `_worker_cap` was written for, that is the OOM the cap was tuned to avoid by hand.
- **Fix:** keep the shapely geometry on the feature (or return a parallel list) and have `check_bands_cover` use it directly instead of `shape(mapping)`; write the tippecanoe input with `shapely.to_geojson(geometry)` per feature as newline-delimited GeoJSON (`tippecanoe -P` reads that in parallel), streaming to the file rather than materialising the dict; delete the `mapping()` call. Consider FlatGeobuf via pyogrio as `emit/water.py:62-86` already does for the coast.

### PR-5 — Per-node Python loops over ~10 M nodes for modes, itinerary and rail detail, with an h3 adjacency test per cell-to-cell predecessor edge and a 480 MB float64 accumulator
- **Severity:** High · **Confidence:** High · **Status:** Confirmed (cost measured at 1/50 scale)
- **Where:** `/Users/hletrd/flash-shared/transport-maps/src/transport_maps/emit/modes.py:60` (`acc = np.zeros((len(minutes), len(CHANNELS)), dtype=np.float64)` — 10 M × 6 × 8 B = 480 MB per worker), `:64-86` (Python loop: `acc[node] = acc[prev]` row copy, `_ground_adjacent(idx.cells[prev], idx.cells[node])` for every cell→cell edge), `:30-38` (`_ground_adjacent`: two `base_parent` calls — each a `get_resolution` and possibly `cell_to_parent` — plus `grid_ring`); `/Users/hletrd/flash-shared/transport-maps/src/transport_maps/emit/itinerary.py:36-45` and `/Users/hletrd/flash-shared/transport-maps/src/transport_maps/emit/rail_detail.py:30-39` (the same distance-ordered Python pass, twice more, each with its own `np.argsort` of 10 M values).
- **Why it is a problem:** a bare per-node pass measured 82 ms per 200 k nodes → ~4 s per 10 M; `_ground_adjacent` measured 2.6 µs per edge → ~26 s per origin over the ~10 M cell→cell predecessor edges (almost every land cell is reached from a neighbouring cell); the `acc[node] = acc[prev]` numpy row assignment adds ~10 M small-array operations. Estimate 45–60 s per origin across the three emitters, plus 480 MB × 5 workers of accumulator.
- **Failure scenario:** none beyond time and memory; but note `acc[node][ROAD_CHANNEL[int(cell_class[node])]] += cost` (`modes.py:79`) indexes `cell_class` by node, so `cell_class` must be the expanded per-cell array — `cli.py:155` passes `ground.cell_class(idx)` which is (good), while the fallback at `modes.py:56-59` calls `roads.cell_class(idx.cells)` on the mixed list, a 10 M-cell footprint pass (~90 s) if any caller ever omits the argument.
- **Fix:** all three are "sum/last-marked-ancestor along the shortest-path tree". Vectorise with pointer jumping over `predecessors`: per node compute the edge contribution `c[node]` (channel, cost) in numpy — mode class is `prev>=first_stn or node>=first_stn` → rail; both cells and `(prev,node)` in the precomputed ferry pair set (`build._ferry_edges` already produces exactly this set; pass it through `shared`) → ferry; both cells otherwise → road channel of `cell_class[node]`; anything else → 0. Then `acc = c`, `jump = pred`; repeat `acc += acc[jump]; jump = jump[jump]` for ⌈log2(depth)⌉ ≈ 25 rounds (masking `jump < 0`). Same doubling gives "nearest arrival-airport ancestor" and "nearest station ancestor". Use `float32`/`uint16` for `acc` (values are clipped to 65534 at `modes.py:108` anyway). This removes ~10 M h3 calls and the three Python passes per origin.

### PR-6 — `_interior` recomputes the band-independent "slowest neighbour" reduction for every band; `_dissolve` runs a full overlay on single already-valid geometries
- **Severity:** High · **Confidence:** High · **Status:** Confirmed (ufunc.at cost measured at 1/50 scale)
- **Where:** `/Users/hletrd/flash-shared/transport-maps/src/transport_maps/contour/bands.py:195-197` (`slowest = np.full(...); np.maximum.at(slowest, rows, band[cols])` — depends on `band`, `rows`, `cols` only, not on `k`), called from `_native_features` (`:246-247`) and `_base_features` (`:218-219`) once per occupied band (~38) per LOD; `:198-201` (rim passes with `np.logical_or.at`); `:120-132` (`_dissolve`: `_crosses_antimeridian` evaluated twice per cell in two list comprehensions, then `unary_union(geoms)` + `make_valid` even when `geoms` is a single geometry straight out of `cells_to_h3shape`).
- **Why it is a problem:** `np.maximum.at` measured 8 ms per 1.2 M edges → ~0.4 s over 60 M native edges; `np.logical_or.at` 15 ms → ~0.7 s. Per origin: native LOD ~38 × (0.4 + 0.7) ≈ 42 s; the two base LODs (23 M edges, rim 1 and rim 3) add ~38 × (0.16 + 0 and 0.16 + 0.55) ≈ 33 s. Roughly 60–90 s per origin, of which the k-independent half is pure recomputation. `unary_union` on one 100 k-polygon multipolygon still nodes every ring (O(n log n) GEOS overlay, seconds per band) and `make_valid` re-validates it; with 38 bands × 4 LODs that is minutes per origin for a no-op in the common case.
- **Fix:** compute `slowest` once per LOD (outside the `for k` loop) and derive `interior_k = (band <= k-1) & (slowest <= k-1)`; for `rim > 1` compute, once per LOD, the "distance to the nearest cell with a slower band" with the same edge list and compare with `rim` per k — or at minimum hoist the first reduction. Replace `ufunc.at` with a sort-based segmented reduction (`np.maximum.reduceat` over `rows` sorted once per LOD), which is typically 5–10× faster than `.at`. In `_dissolve`, evaluate `_crosses_antimeridian` once per cell, and when there is exactly one geometry and no wrapping cells, return it after a single `is_valid` check instead of `unary_union` + `make_valid`.

### PR-7 — Forked workers un-share the 10 M-entry `cells` list and `_cell_pos` dict through refcount traffic, which is what caps the build at 5 workers
- **Severity:** High · **Confidence:** Medium · **Status:** Likely (mechanism is documented in the code itself; magnitude estimated)
- **Where:** `/Users/hletrd/flash-shared/transport-maps/src/transport_maps/graph/nodes.py:42-44` (`cells: list[str]`, `_cell_pos: dict[str, int]`), `:60` (`base_cells: list[str]`), `:123` (`cell_pos = {c: i ...}`); `/Users/hletrd/flash-shared/transport-maps/src/transport_maps/cli.py:70-74` (`_worker_cap`: "at ten million cells eight workers exceed 32 GB") and `:54-60` (the refcount explanation).
- **Why it is a problem:** 10 M 15-character `str` objects (~64 B each) plus the list (80 MB) plus a 10 M-entry dict (~1 GB) live in the parent. Every emitter iterates `idx.cells` (`hover.py:44`, `modes.py:78`, `validate.py:34`, `bands.py:237` `np.array(idx.cells, dtype=object)`), so every worker touches the refcount of every string and dirties essentially every page holding them: ~1.5–2 GB of copy-on-write un-sharing per worker on top of its own arrays. The cap of 5 (instead of 8, `cli.py:67`) is a 60 % wall-clock penalty on a 10-hour build, and PR-3/PR-5 stack their own transient GBs on top.
- **Fix:** store cells as `np.uint64` (`h3.str_to_int`) and keep a sorted copy with a permutation for lookup (`np.searchsorted`); convert to `str` only at the API boundary (`cell_index(cell: str)` → `str_to_int` then searchsorted, ~1 µs). `base_index`, `fine`, `parent_res4`, `centroids` (lat/lon float32) all belong in `shared` as numpy arrays. With no Python objects to refcount, the fork stays shared and `_worker_cap` can go back to `min(cores-2, 8)`.

### PR-10 — The `mousemove` frame does `queryRenderedFeatures`, two full gazetteer scans, three `innerHTML` writes and a forced layout, under `backdrop-filter: blur` panels
- **Severity:** Medium · **Confidence:** Medium · **Status:** Likely (cost pattern is well known; needs a Performance-panel trace to quantify on this page)
- **Where:** `/Users/hletrd/flash-shared/transport-maps/web/app.js:611-639` (handler: rAF-throttled, good; but per frame `bandRangeAt(e.point)` → `:578-595` `map.queryRenderedFeatures(point, {layers:["bands"]})`, `describe()` → `nearestPlace()` at `:599`, then a second `nearestPlace()` at `:628`, `$("time").innerHTML`, `$("where").innerHTML`, `tip.innerHTML`, then `tip.offsetWidth` at `:635` — a synchronous layout after the DOM writes — then `style.left/top`); `bandRangeAt` runs even when `t == null` (ocean) at `:619` before the early return at `:626`. `/Users/hletrd/flash-shared/transport-maps/web/index.html:122-123`, `:132-133`, `:218-220` (`backdrop-filter: blur(10px)` on `.mast`, `.reading`, `.tip`, all sitting on a WebGL canvas that repaints continuously during drag/zoom).
- **Why it is a problem:** `queryRenderedFeatures` hit-tests every feature in every visible tile of the `bands` layer and deserialises matching features from the vector tiles; on the cumulative low-zoom bands (37 overlapping polygons per tile) it returns dozens of features per call. It only changes when the solved cell under the pointer changes, yet it runs every animation frame the mouse moves. `nearestPlace` is a 31 k-iteration scalar loop (`:238-244`) executed twice per frame for the same point. The `offsetWidth` read after three `innerHTML` writes forces layout every frame. Each `backdrop-filter` region is re-blurred by the compositor whenever the canvas beneath changes, i.e. every frame of every pan on integrated GPUs. - **Fix:** gate `bandRangeAt` and `nearestPlace` on `cell !== hoveredCell` (the readout cell), cache `{band, place}` per hovered cell; call `nearestPlace` once and reuse; skip `bandRangeAt` entirely when `t == null`; write the tip text, then read `offsetWidth` only when the text length bucket changes (or position with `transform` and let CSS `right: auto` flip via a class); drop `backdrop-filter` on `pointer: coarse` and `prefers-reduced-transparency`, or use a solid `color-mix` at 90 % (the design policy asks for a dark scrim, not a blur).

### PR-11 — 900 DOM markers for place labels, re-projected in a JS loop on every `move` frame, on top of MapLibre's own per-marker `move` listeners
